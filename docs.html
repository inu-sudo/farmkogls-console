1단계 — 제가 이해한 팜코지엘에스의 업무와 데이터

이 문서는 제공해주신 13개 엑셀 파일과 알려주신 내용(회사명, 부킹 사이트, "일부 항로는 사이트가 아니라 이메일 엑셀로 처리")을 근거로 재구성한업무 모델입니다. 이 이해가 도구 설계의 전제이므로, 틀린 부분이 있으면이 문서를 먼저 고쳐야 합니다.

1. 회사가 하는 일

팜코지엘에스(Farmkogls, 데이터상 FARMKO / 팜코)는 선박을 소유하지 않는 NVOCC / 선복 재판매업자입니다.

  피더 선사              팜코지엘에스                고객
  (GFS/BTL/X-Press)  ──▶  선복 블록 매입      ──▶  한국 포워더
   실제 배 운항            (DF 계약)                해외 에이전트
                          ↓
                    남은 선복 = 손실
                    초과 선복 = 추가비용

핵심 구조는 DF(Dead Freight, 부동운임) 계약입니다.

  • 선사와 기간(보통 1~6개월)을 정해 약정 물량(TEU)과 약정 중량(톤)을 삽니다.
  • 대금은 TEU당 단가 × 약정 물량으로 고정됩니다. → 안 채우면 그대로 손실.
  • 약정을 넘겨 실으면 Excess Slot Rate(구간별 별도 단가)가 붙습니다.
  • 여기에 할증이 더해집니다: DG 150/TEU, RF 150/box, Flexi 100/box, TK 100/box, COD 130/변경.

따라서 이 회사의 손익은 "약정 대비 실제 적재율"에서 거의 다 결정됩니다. BSA를 넘겼는지 남겼는지가 곧 돈입니다. 제가 만든 도구가 화면 한가운데에 BSA 대비 이용률을 놓은 이유입니다.

실제 예 (BTL_CCS(JUL 26') 시트):

항목값
단가850 / TEU
약정 물량70 TEU
약정 중량910 톤 (상해 720 톤)
고정 대금59,500
실제 적재69 TEU → 실질 단가 862.3 / TEU
판매 단가20' 1,500 / 40' 1,900

같은 시트의 "#1. Ideal Booking" 시나리오는 −16,000 입니다. 즉 어떤 박스를 싣느냐에 따라 흑자와 적자가 갈립니다. 40'를 이상적으로 채우면적자, 실제처럼 20'를 섞으면 흑자였습니다.

4. 반드시 지켜야 하는 계산 규칙

파일의 실제 수식에서 그대로 뽑았습니다. 도구도 동일하게 구현했습니다.

TEU 환산 — 20피트류 1, 40피트류 2, Void 1

TEU = 20'DV + 20'MT + 20'FR + Void + (40'HC + 40'MT + 40'FR) × 2

Void가 1 TEU로 계산되는 게 중요합니다. OOG(초과규격) 화물이 옆 슬롯을못 쓰게 만드는 만큼을 비용으로 잡는 것입니다.

주차(WK) — 엑셀 WEEKNUM(ETD) 기본값(일요일 시작, 1월 1일이 1주차). ISO 주차와 다릅니다. 파일과 숫자를 맞추려면 이 방식이어야 합니다.

Tare(공컨 자중) — 20FT 2.3톤, 40FT 3.7톤

화물 등급 — FR이나 Void가 있으면 OOG, 특수/비고에 위험물 표기가 있으면 DG, 나머지는 NDG

ROB(선상 잔량) — 이게 가장 중요한 개념입니다.

각 기항지에서:  잔량 = 이전 잔량 + 이번 적재 − 이번 양하
잔여 선복    =  BSA − 최대 선상 잔량

"부킹 합계"가 아니라 "최대 선상 잔량"이 선복 소요량입니다. 부산에서 실어 첸나이에서 내린 박스는 그 이후 구간의 선복을 쓰지 않습니다. 실제 예 — TIGER CHENNAI 2605W는 부킹 합계 105 TEU지만최대 선상 잔량은 81 TEU입니다. 귀사 BK SHEET의 Grand Total도 81입니다. BSA가 50이므로 초과는 31 TEU(합계 기준 55가 아님)입니다. 이 차이만큼 초과 선복 비용을 과다 계산할 수 있습니다.

5. 지금 방식의 구조적 문제

부킹 사이트(farmkogls.plism.com)가 있는데도 엑셀을 주고받는 이유가 "일부 항로만 사이트에서 처리된다"는 것이었습니다. 그래서 생기는 문제:

  1. 같은 부킹이 3곳에 존재 — 에이전트 예보, 통합 등록부, 항차 BK SHEET. 서로 값이 어긋나도 알 방법이 없습니다. 실제로 지금 파일에 16건의 불일치가 있습니다.
  2. 수식이 조용히 깨져 있음 — FES BK FCST의 VGM 계산 중 16·21·23·24·30·31·37·38·39행이 빈 셀 $V$4/$V$5를 참조해 중량이 0으로나옵니다(정상인 26·29행은 $Z$4/$Z$5). 중량 초과 판단이 무력화됩니다.
  3. 표기 불일치 — 같은 항구가 MYPKG(N) / MYPKN / NPKL, 같은 회사가 FARMKO / 팜코, 오타 CHSHA(→CNSHA), X-PRESS PHOEINIX, MELBOURNE BRDIGE. → 집계하면 각각 다른 항목으로 잡힙니다.
  4. 헤더 오타가 실적을 왜곡 — BK SHEET 5장의 SVC Name이 잘못 적혀 80건의 부킹이 엉뚱한 서비스로 집계되고 있었습니다. 예: XCA26022W(0615)마감은 CSC로 적혀 있지만 X-PRESS CARINA는 NWX 선박입니다.
  5. 항차 번호가 매년 재사용됨 — WAN HAI 522 W038이 25년과 26년에 모두존재합니다. 연도 구분 없이 합치면 과거 BSA가 현재 항차를 덮어씁니다.
  6. 초과 적재가 집계되지 않음 — 지금 데이터에서 27개 항차가 BSA 초과, 합계 476 TEU입니다. 의도된 초과일 수도 있지만, 한눈에 보이지 않으면협상·정산 근거가 없습니다.

7. 아직 확인이 필요한 부분 (제 추정)

  1. Last upload — 방금 넣은 파일별로 몇 건 읽었고 어떤 시트를 못 읽었는지.
  2. Source disagreements — ⭐ 가장 중요. 같은 부킹인데 파일마다 값이 다른 경우를 양쪽 출처(파일 › 시트)와 함께 나열합니다. 어느 쪽을 채택했는지도 표시됩니다. 손으로 확인해야 할 목록입니다.
  3. Merge history — 배치별 신규/변경/동일/취소/중복접힘/누적 이력.
  4. Row-level changes — 어느 B/L의 어느 항목이 무엇에서 무엇으로 바뀌었는지.

⚠️ 등록부는 사람마다 따로입니다

홈페이지로 열든 파일로 열든, 등록부는 그 브라우저에만 쌓입니다. 공유 서버가 없기 때문입니다.

  • 같은 홈페이지를 두 사람이 열어도 서로의 등록부는 보이지 않습니다.
  • 회사 PC에서 넣은 파일은 집 PC에서 안 보입니다.
  • 브라우저 기록을 지우면 등록부도 같이 지워집니다.

여럿이 같은 등록부를 봐야 한다면 Save project file로 .json을 만들어공유 폴더나 메일로 넘기고, 받은 쪽이 그걸 드롭하면 됩니다. 이게 현재 유일한 공유 방법입니다. (실시간 공유가 필요하면 별도 작업입니다 — 서버가 생기고, 그러면 보안 검토가 따라옵니다.)

3. 왜 이렇게 만들었나 — 핵심 결정들

각 결정마다 "다르게 했다면 어떻게 됐을까"를 붙였습니다. 설명할 때 이 대비가 제일 잘 먹힙니다.

① 설치가 필요 없는 파일 하나로

다르게 했다면 — 서버를 세우고 계정을 만들고 사내 IT 승인을 받아야 합니다. 담당자가 바뀌면 인수인계에 "이 서버 관리법"이 추가됩니다.

이렇게 한 이유 — 이 PC에는 개발 도구가 하나도 깔려 있지 않았습니다. 프로그램 설치 권한이 없거나 IT 승인이 오래 걸리는 환경에서도 더블클릭 한 번으로 돌아가야 했습니다. 파일 하나(192KB)라서메일로 보내면 그게 곧 배포입니다.

② 인터넷을 전혀 쓰지 않음

다르게 했다면 — 부킹 데이터, 고객명, 운임이 외부 서버를 거칩니다. "이 도구 써도 되나요?"를 보안팀에 물어야 합니다.

이렇게 한 이유 — 실을 수 있는 물량, 판매 단가, 거래처 목록은 경쟁 정보입니다. 외부로 나가는 통신이 한 건도 없게 만들었습니다. 와이파이를 끄고 써도 똑같이 동작합니다. 이건 IT 담당자에게 "통신 안 합니다"로 한 문장에 설명됩니다.

이 때문에 엑셀을 읽고 쓰는 기능을 남의 라이브러리 안 쓰고 직접 만들었습니다. 라이브러리를 쓰면 그걸 인터넷에서 받아와야 하거나 파일이 5배로 커집니다.

③-0. 파일을 새로 만들지 않고, 기존 파일을 고침 ⭐⭐

다르게 했다면 — "통합 결과"라는 새 엑셀을 하나 만들어 줍니다. 그런데 그건담당자가 쓰던 등록부가 아닙니다. 수식도 서식도 그림도 메모도 없는 딴 파일입니다. 결국 사람이 그걸 보고 원래 등록부에 다시 옮겨 적어야 합니다. 일이 안 줄어듭니다.

이렇게 한 이유 — 원하는 건 "새 보고서"가 아니라 "내 파일이 갱신된 것"입니다. 그래서 대상 파일을 통째로 다시 만들지 않고, 필요한 칸만 골라서 고칩니다.

집을 새로 짓는 게 아니라 벽지만 바르는 것에 가깝습니다. 건드리지 않은 부분은 1비트도 바뀌지 않으니 수식·서식·그림·메모가 원래대로 남습니다.

행을 새로 끼워 넣을 때 따라 움직여야 하는 것들이 있습니다 — 아래쪽 수식의 행 번호, 조건부 서식 범위, 메모 위치, 자동 필터 범위, 정의된 이름. 엑셀이 손으로 삽입할 때해주는 일을 프로그램이 대신 합니다. 실제 파일에서 그 항목이 11가지였고, 전부열거해서 하나씩 맞췄습니다. 검증은 엑셀로 직접 열어서 했습니다 — "복구가 필요합니다" 없이 열리고, 새 행의 수식이 실제로 계산되고, Schedule 시트 셀 차이가 0이어야 통과입니다.

③ 엑셀을 없애지 않고, 엑셀을 그대로 씀 ⭐

다르게 했다면 — "이제 엑셀 그만 쓰고 이 시스템에 직접 입력하세요"가 됩니다. 해외 에이전트, 선사, 한국 포워더 전부를 설득해야 합니다. 실패합니다.

이렇게 한 이유 — 엑셀 주고받기는 없앨 수 없는 현실입니다. 상대가 우리 시스템을 쓸 이유가 없으니까요. 그래서 도구는 받는 엑셀도 그대로, 보내는 엑셀도 그대로입니다. 내보낸 파일의 열 순서를 귀사 FES BK FCST와 똑같이 맞춘 게 그 이유입니다. 받는 쪽에서는 뭐가 바뀐 줄도 모릅니다.

바뀌는 건 중간의 손작업만 입니다.

④ 원본 값을 절대 고치지 않음

다르게 했다면 — 도구가 "이 서비스는 틀렸으니 고쳐놨습니다" 하고값을 바꿔버립니다. 나중에 원래 뭐였는지 알 수 없습니다.

이렇게 한 이유 — 원본은 그대로 두고, 보정한 값을 옆 칸에 따로 둡니다. 집계는 보정값으로 하고, 화면에는 ⚑ 표시를 붙여 "원본은 이랬다"를 볼 수 있게 합니다.

이걸 어겼다가 실제로 사고가 났습니다 — 원본을 덮어쓰니까, 다음에 같은 파일을 넣으면 원본이 다시 자기 값을 주장하고, 또 고치고, 무한 반복됐습니다(§5-③).

⑤ 값이 충돌하면 조용히 정하지 않음

다르게 했다면 — 도구가 알아서 하나 고릅니다. 편하지만, 틀렸을 때 아무도 모릅니다.

이렇게 한 이유 — 규칙대로 하나를 고르되 버린 값과 양쪽 출처를 전부 기록합니다. Changes › Source disagreements와 엑셀 DATA QUALITY 시트에 "이 B/L의 ETD가 A파일은 7/31, B파일은 7/27. 7/31을 썼습니다"가 남습니다.

통합 도구의 신뢰는 여기서 결정됩니다. 사람이 모르게 값을 고르기 시작하면아무도 결과를 믿지 않습니다.

⑥ 주소로 나눠주되, 자료는 올리지 않음

다르게 했다면 — 흔히 하는 방식은 자료까지 서버에 올려서 모두가 같은 화면을보게 하는 것입니다. 편리합니다. 그런데 그 순간 부킹 자료가 남의 컴퓨터에저장됩니다. 유출되면 우리 책임이고, 보안 검토·계약·비용이 전부 따라옵니다.

이렇게 한 이유 — 나눠줄 게 도구뿐이지 자료가 아니라는 점을 이용했습니다. 홈페이지는 도구를 배달만 하고, 배달이 끝나면 그때부터는 방문자 브라우저안에서만 돌아갑니다. 서버는 자료를 받지도, 보관하지도 않습니다. 설계 ②(외부 통신 없음)를 깨지 않고 "아무나 접속"을 얻은 것입니다.

값은 있습니다 — 등록부가 사람마다 따로 쌓입니다. 실시간 공유가 안 됩니다. 지금은 .json 파일을 주고받는 게 유일한 공유 방법입니다. 이건 감춘 게 아니라 의도한 교환이고, 매뉴얼 §7에 그대로 적어뒀습니다.

PIN에 대해서는 부풀리지 말아야 합니다.

이 4자리는 자물쇠가 아니라 문고리입니다. 검사가 방문자 브라우저 안에서일어나므로, 마음먹고 뜯어보면 통과할 수 있습니다. 막아주는 것은 "주소를 우연히 아는 사람이 그냥 들어오는 것"까지입니다.

그래도 이렇게 둔 이유는 홈페이지에 자료가 없기 때문입니다. 지켜야 할 게비어 있는 도구뿐이라 위험이 낮습니다. 자료를 올리게 되는 순간 이 판단은 즉시 무효가 되고, 그때는 진짜 인증(이메일 확인 등)이 필요합니다.

이걸 설명할 때 절대 하지 말아야 할 말: "PIN 걸어놨으니 안전합니다." 정확한 말은 "안에 지킬 자료가 없고, PIN은 우연한 방문을 막는 용도입니다."

4. 가장 중요한 아이디어 3개

기술이 아니라 업무 통찰입니다. 이 셋만 이해하면 도구를 다 이해한 겁니다.

① 선복은 "합계"가 아니라 "최대 동시 점유" — 호텔 객실과 같다 ⭐⭐

호텔에 한 달간 100명이 묵었다고 방 100개가 필요한 게 아닙니다. 같은 날 밤에 최대 몇 명이 있었는지가 필요한 방 수입니다.

배도 똑같습니다. 부산에서 실어 첸나이에서 내린 컨테이너는 그 이후 구간의 선복을 쓰지 않습니다.

실제 숫자로:

TIGER CHENNAI 2605W
부킹 합계105 TEU
최대 동시 적재81 TEU ← 실제 필요한 선복
BSA(우리 배정)50 TEU
초과31 TEU (합계로 보면 55로 착각)

귀사 BK SHEET의 Grand Total도 81입니다. 즉 원래 이렇게 세고 계셨고, 도구가 그걸 자동화한 것입니다. 합계로 계산하면 초과 선복 비용을 24 TEU만큼 과다 계상합니다.

그래서 화면에 Booked TEU와 Peak TEU를 나란히 놓았습니다. 정산 근거는 항상 Peak입니다.

② 같은 부킹인지 어떻게 알아보나 — 주민번호가 있는 사람과 없는 사람

세 파일에 흩어진 부킹이 "같은 건"인지 판단해야 합니다.

B/L 번호가 있으면 쉽습니다 — 주민번호처럼 씁니다. B/L번호 + 선명·항차 + 양하항이 같으면 같은 건.

문제는 B/L이 없는 행입니다. 공컨 회수는 B/L 자리에 MT, FULL, T.B.N처럼 적혀 있습니다. 주민번호 없는 사람을 구별하는 셈입니다. 그래서 얼굴 특징을 조합합니다 — 항차 + 구간 + 거래처 + 박스 구성 + 비고, 그리고 "그 시트에서 몇 번째로 나온 같은 모양인지".

마지막 조건이 없으면 사고가 납니다. 같은 시트에 똑같이 생긴 공컨 3줄이실제로는 별개 부킹인데 1줄로 뭉개집니다. 실제로 3건 7 TEU가 사라지고 있었습니다(§5-①).

부작용도 정직하게: 그 행의 비고를 고치면 새 행처럼 보입니다. 매뉴얼 §9에 적어뒀습니다.

③ 파일 넣는 순서가 결과를 바꿔선 안 된다 — 장부는 정리 순서와 무관하다

영수증을 어떤 순서로 정리하든 월말 합계는 같아야 합니다. 당연한데, 프로그램에서는 당연하지 않습니다.

처음엔 파일을 들어오는 대로 둘씩 합쳤습니다. 그러면 이런 일이 생깁니다:

빈칸을 신뢰도 낮은 파일이 먼저 채워버리면, 나중에 온 신뢰도 높은 파일이 더 이상 고칠 수 없습니다.

정순으로 넣으면 선명이 X-PRESS PHOENIX, 역순으로 넣으면 X-PRESS PHOEINIX가됐습니다. 같은 데이터인데요.

해결 — 둘씩 합치는 걸 버리고, 같은 부킹의 사본을 전부 모아놓고신뢰도 순으로 줄 세운 다음, 항목마다 "값을 가진 가장 신뢰도 높은 사본"에서 가져옵니다.

신뢰도 순서(설명할 때 이대로 쓰면 됩니다):

  1. 항차별 마감 시트 — 실제 선적 확정본이니 가장 정확
  2. 통합 등록부 / 에이전트 예보 — 같은 등급
  3. 같은 등급이면 더 최근에 저장된 파일
  4. 그래도 같으면 파일명 순서 (결과가 항상 같게 하려고)

검증: 정순·역순·섞은 순서 세 가지가 완전히 동일한 결과. 9가지 파일 조합을 반복 투입해도 변경 0건.

5. 실패에서 배운 것 (비개발자에게 설명하기 좋은 사례)

"AI로 만들었는데 믿을 수 있나요?"라는 질문에 대한 답이 이 절입니다. 만드는 동안 조용히 틀린 답을 내던 문제 10개를 찾아 고쳤습니다. 전부 에러 메시지 없이, 그럴싸한 숫자를 내놓고 있었습니다.

대표 3개만 (전체는 부록 §5):

① 부킹 3건이 사라지고 있었음

B/L 자리에 FULL이라고 적힌 행 8개를 프로그램이 "빈칸"으로 못 알아봤습니다. 그래서 서로 다른 부킹 3건이 1건으로 합쳐졌습니다. 7 TEU가 조용히 사라졌습니다. → 교훈: 업무 파일의 "빈칸"은 진짜 빈칸이 아니라 관용어다.

② 같은 화물을 두 번 실었다고 계산

CCS 항로는 청도와 부산을 두 번 기항합니다. 프로그램이 항구 이름만 보고매칭해서, 첫 기항에서 실은 화물을 마지막 기항에서 또 실었습니다. 필요 선복이 42 TEU인데 75 TEU로 계산됐습니다. → 교훈: 항로는 "항구 목록"이 아니라 순서가 있는 여정이다.

③ 같은 파일을 넣을 때마다 값이 바뀜

"이 서비스 표기가 틀렸다"고 판단해서 원본을 고쳐놨더니, 다음에 같은 파일을 넣으면 원본이 다시 자기 값을 주장하고, 또 고치고, 영원히 왔다갔다 했습니다. → 교훈: 읽은 값과 계산한 값을 섞지 말 것.

④ 버튼이 하나도 안 눌리고 있었음 ⚠️ (가장 부끄러운 것)

화면을 만들 때, 존재하지 않는 버튼(btnLoadProj)에 기능을 붙이는 코드가한 줄 있었습니다. 그 한 줄에서 오류가 나면서 그 뒤에 등록되는 모든 클릭 기능이통째로 죽었습니다. 탭 전환도, 정렬도, 실행 버튼도 전부 안 눌렸습니다.

그런데 오랫동안 못 찾았습니다. 제가 검증할 때 화면을 "그려지는지"만 확인하고버튼은 프로그램으로 우회해서 눌렀기 때문입니다. 사람이 실제로 클릭하는 경로를한 번도 안 밟았습니다.

→ 교훈 둘:

화면이 그려지는 것과 눌리는 것은 다른 문제다. 반드시 실제로 클릭해서 확인.

그리고 한 곳의 오류가 다른 기능까지 죽이지 않게 만들어야 합니다. 이제는 없는 버튼을 만나면 그 하나만 건너뛰고 경고를 남깁니다.

⑤ 배포 스크립트가 "정상"을 오류로 알아듣고 죽었음

홈페이지를 올리는 스크립트에 "저장소가 이미 있는지 확인" 단계를 넣었습니다. 첫 배포에서는 당연히 없는 게 정답인데, 확인 명령이 "없습니다"를오류 형태로 출력했고, 스크립트가 그걸 진짜 오류로 받아 그 자리에서 멈췄습니다.

제가 시험한 건 "저장소가 있을 때"뿐이었습니다. 한 번도 안 해본 첫 실행에서바로 터진 것입니다.

→ 교훈:

"아무 문제 없을 때"만 시험하면, 문제 있을 때 죽는 걸 못 봅니다. 특히 처음 한 번만 지나가는 경로(최초 실행, 빈 상태, 최초 설치)는개발 중에 가장 안 밟아보는 길이면서 사용자가 반드시 첫 번째로 밟는 길입니다.

⑥ 문에 비밀번호를 적어 붙여놨음 ⚠️

PIN을 빌드 스크립트 안에 PIN = "...." 로 적어뒀습니다. 그 스크립트는소스의 일부라서 공개 저장소에 같이 올라갔습니다. 게다가 제가 매뉴얼에 "PIN ○○○○을 누르세요"라고 친절하게 써서 그것까지 같이 올렸습니다.

자물쇠를 달고 열쇠를 문에 테이프로 붙여놓은 셈입니다.

고친 방법:

  1. PIN을 pin.txt 파일 하나로 빼고, 그 파일은 저장소에 못 올라가게 막음
  2. 빌드할 때마다 결과물에 PIN 숫자가 들어 있으면 빌드를 거부
  3. 문서에서는 숫자를 빼고 "담당자에게 확인하세요"로 바꿈

→ 교훈:

비밀은 "안 적으면 된다"가 아니라 "적을 수 없게 만들어야" 지켜집니다. 사람이 조심하는 것에 기대면 언젠가 새어 나갑니다. 기계가 막게 하세요.

그리고 한 번 공개된 비밀은 지워도 되돌아오지 않습니다. git은 파일을 지워도 과거 커밋에 남습니다. 새어 나갔으면 지우는 게 아니라 바꿔야 합니다.

그래서 검증을 5중으로 걸었습니다

단계확인하는 것
1원본 파일로 전 과정 실행 + 알려진 셀 값 18개 대조
2같은 파일 반복 투입 → 변경 0건이어야 통과
3파일 순서를 바꿔도 → 완전히 같은 결과여야 통과
4실제로 클릭해서 탭·버튼·정렬·필터가 다 동작하는지 (④의 교훈)
5엑셀로 실제로 열어서 복구 없이 열리는지, 수식이 계산되는지, 한글이 살았는지

5번이 최종 관문입니다. 확인한 것:

  • 분석 리포트: 엑셀이 계산한 합계 4,920 TEU가 3개 시트에서 전부 일치
  • 파일 갱신: "복구가 필요합니다" 없이 열림, 새 행의 =WEEKNUM·TEU 수식이실제 계산됨, 서식·그림·메모 보존, Schedule 시트 셀 차이 0, TEU 합계 증가분 116이 신규 11행 합계와 정확히 일치

접근 제어는 4자리 PIN이며, 브라우저 쪽 검사입니다. 인증이 아니라우연한 접근을 막는 수준으로만 봐 주십시오. 그렇게 둔 근거는 공개되는 쪽에 지킬 자료가 없다는 점입니다. 자료를 올려야 하는요건이 생기면 그 시점에 실제 인증(예: Cloudflare Access의 이메일 확인)을앞단에 두는 것이 맞습니다.

1. 설계 전제 3가지

1-1. 의존성 0

npm install 하나 없습니다. 이유:

  • 이 PC에는 Node도 Python도 없었습니다(PATH의 python.exe는 Microsoft Store 스텁이라 실행되지 않음). 담당자가 바뀌어도 동작해야 합니다.
  • 데이터가 상업 기밀입니다. 외부로 나가는 요청이 하나도 없어야 합니다.
  • 5년 뒤에도 열려야 합니다. CDN이 죽으면 도구가 죽는 구조는 피했습니다.

그래서 .xlsx 읽기/쓰기를 직접 구현했습니다.

  • 읽기 — 브라우저 내장 DecompressionStream('deflate-raw')로 ZIP 해제 (SheetJS 약 900KB를 넣지 않아도 됨)
  • 쓰기 — ZIP을 STORE(무압축) 방식으로 생성 + CRC32 직접 계산. 엑셀은 무압축 xlsx도 문제없이 엽니다.

1-2. 원본을 덮어쓰지 않고 파생시킨다

소스에서 읽은 값(svc1)은 절대 수정하지 않고, 보정값은 별도 필드(svcEff)에둡니다. 한 번 원본을 덮어썼다가 무한 진동 버그를 만들었습니다(§5-8 참조).

1-3. 조용히 해결하지 않는다

값이 충돌하면 규칙대로 하나를 고르되, 버린 값과 양쪽 출처를 반드시 기록합니다 (Changes › Source disagreements, DATA QUALITY 시트). 통합 도구가 사람 모르게 값을 고르기 시작하면 신뢰를 잃습니다.

4. 핵심 알고리즘 3개

4-1. 레이아웃 판별 (parse.js)

시트 이름에 의존하지 않습니다(마감, (0726), 오타 등으로 이름이 제각각). 헤더 행을 찾아 그 내용으로 판별합니다.

1~40행을 훑어 각 행을 점수화
  헤더 텍스트를 정규 필드명으로 매핑 (H_EXACT 사전 + 느슨한 패턴)
  조건: 매칭 6개 이상 + 컨테이너 열 2개 이상 + B/L 열 존재
  → 최고점 행이 헤더

판별:
  '1st Leg Vessel' 있음                    → masterForecast
  'Pick Up' / 'Cancel Date' / 'Shipper' 등 → bkSheet
  'Vessel' + 'Voy' 분리                    → agencyForecast
  'VSL/VOY' + 'WK' 반복                    → schedule
  'NORTHBOUND/SOUTHBOUND'                  → bsa
  'DF Contract' + 'RATE :'                 → dfContract
  'TOTAL(Incl. ROB)' / 'OOG(Void)'         → rob

열 위치가 파일마다 밀려도 견딥니다. 새 양식 대응은 대부분 H_EXACT에 헤더 문자열 한 줄 추가로 끝납니다.

데이터 행 종료 조건이 의외로 까다롭습니다. 데이터 구역 안에소계·합계·Cancel 정리·헤더 재출력이 섞여 있습니다(TOTALS_HINT_RE, CANCEL_SECTION_RE).

4-2. 그룹 병합 (merge.js)

같은 부킹이 최대 3곳에 존재합니다. 2개씩 순차로 합치면 순서 의존이생깁니다(§5-7). 그래서 전량을 모아 한 번에 해결합니다.

// 1) 키로 전부 모은다
groups: key → [copy1, copy2, copy3]

// 2) 신뢰도 순으로 정렬 (완전 결정적)
byPrecedence =
  레이아웃 등급 내림차순            // bkSheet 3 > master/agency 2 > 기타 1
  → 파일 수정시각 내림차순          // 같으면 최근 저장분
  → 파일명 → 시트명 → 행번호        // 그래도 같으면 이름순

// 3) 필드별로 "값을 가진 가장 좋은 사본"에서 가져온다
for (필드 of 텍스트+숫자) if (lead[필드] 비어있음) 뒤에서 첫 유효값

// 4) 박스 수량은 세트로 이동 (7개를 쪼개면 TEU가 깨짐)
// 5) 하나라도 cancel이면 cancel
// 6) MATERIAL 필드가 서로 다르면 conflicts[]에 기록

키 설계가 이 파일의 진짜 어려운 부분입니다.

B/L 있음  → 'B|' + 정규화B/L + '|' + 선명|항차 + '|' + POD
B/L 없음  → 'X|' + (항차|구간|거래처|박스구성|비고해시) + '|#' + 등장순번

MT / FULL / T.B.N 같은 자리표시자는 문서번호가 없습니다. 등장 순번을 키에 넣은 이유: 같은 시트에 똑같이 생긴 공컨 회수 3줄이실제로는 별개 부킹입니다. 순번이 없으면 1줄로 뭉개져 물량이 사라집니다 (실제로 3건 7 TEU가 사라지고 있었습니다). 반면 순번을 시트별로만 매기므로, 같은 줄이 다른 파일에 또 나오면 양쪽 #1이라 정상 병합됩니다.

4-3. ROB 재계산 (aggregate.js)

수작업 ROB 시트를 읽는 대신 부킹에서 다시 만듭니다.

rotation = 그 항차의 스케줄 기항순서 (없으면 서비스 기본 순서)

// 각 부킹을 정확히 한 번만 적재
for (부킹) loadIdx[부킹] = rotation에서 POL이 처음 나오는 위치

// 기항지 순서대로
for (i, 기항지 of rotation) {
  적재 = loadIdx === i 인 부킹들
  양하 = 하선항 === 기항지 && loadIdx < i && 아직 안 내린 부킹들
  선상 += 적재 − 양하
}
선복소요 = max(선상)          // ← 합계가 아니라 최대값
잔여     = BSA − 선복소요

loadIdx가 핵심입니다. CCS·NWX 루프는 청도와 부산을 두 번 기항합니다. 항구 이름만으로 매칭하면 같은 화물을 두 번 싣습니다(§5-3).

5. 실제로 만난 버그와 교훈 ⭐

이 절이 이 문서의 핵심입니다. 전부 실제 발생했고, 전부 조용히 틀린 답을내놓던 종류입니다.

5-1. 병합셀이 자기 라벨을 되돌려줌

  • 증상: 존재하지 않는 서비스 SVCNAME이 2,834 TEU를 차지.
  • 원인: sh.get()이 병합 영역을 해석해준다 → A10:B11이 병합된 "SVC Name :" 라벨에서 오른쪽 B10을 읽으면 라벨 자신이 돌아옴. canonSvc("SVC Name :") → "SVCNAME".
  • 수정: 라벨과 텍스트가 같은 셀은 건너뛴다(valueRightOf).
  • 교훈: 병합셀을 해석해주는 편의 기능이 "라벨 오른쪽 값 읽기"와 충돌한다.

5-2. 합계 행이 부킹으로 들어옴

  • 증상 : 한국 선적 합계 → 한국 선적 합계 라는 유령 구간 287 TEU.
  • 원인: 합계 행이 데이터 구역 안에 있고, 종료 판정이 영어 키워드만 봤음.
  • 수정: 합계|소계|GRAND TOTAL|ACCOUNT NO|… 로 확장.
  • 교훈: 한국어 업무 파일은 요약 행이 데이터 중간에 끼어 있다. 영어 키워드만보면 반드시 새어 들어온다.

5-3. 순환 항로에서 화물을 두 번 실음

  • 증상: KMTC JEBEL ALI 2602W 최대 선상 75 TEU (실제 42).
  • 원인: 적재를 항구 이름으로 버킷팅. CCS 루프는 청도·부산을 두 번 기항하므로같은 화물이 1번째와 9번째 기항에서 모두 적재됨.
  • 수정: 부킹별 loadIdx를 한 번만 배정, 양하는 그보다 뒤 기항에서만.
  • 검증: TIGER CHENNAI 2605W 최대 81 TEU = 귀사 BK SHEET Grand Total 81. ✅
  • 교훈: 항로는 그래프가 아니라 순서 있는 목록이다. 같은 노드가 재등장한다.

5-4. 항차 번호 재사용

  • 증상: WAN HAI 522 W038의 BSA가 73이어야 하는데 60으로 나옴.
  • 원인: 25년 ROB 시트와 26년 BK SHEET가 같은 선명|항차 키.
  • 수정: BSA 출처에 등급 부여(항차 BK SHEET 3 > 스케줄 2 > 과거 ROB 1).
  • 남은 한계: 근본 해결은 키에 연도를 넣는 것. 지금은 시즌별로 등록부를나누라고 매뉴얼에 명시.
  • 교훈: 업무 식별자는 대개 재사용된다. "고유해 보이는 번호"를 믿지 말 것.

5-5. 소스에 박힌 제어문자가 모듈 하나를 통째로 죽임 ⚠️

  • 증상: 번들 파일에서 FXlsxWrite가 undefined. 개별 파일 로드는 정상.
  • 원인: esc() 안에 /[\x00-\x08…]/ 를 쓰려 했는데 파일에 실제 제어 바이트가들어감. <script src>로는 파싱되지만, 번들러의 텍스트 왕복을 거치면정규식 리터럴이 깨져 그 모듈만 조용히 실패.
  • 수정: 정규식을 버리고 코드포인트로 필터(stripCtl). 그리고 build.py가 제어문자 포함 소스를 아예 거부하도록 방어선 추가.
  • 교훈: 가장 무서운 버그는 "한 군데만 조용히 안 되는" 버그다. 재발 방지를 코드가 아니라 빌드 단계에 심어야 한다. (이 방어선은 실제로 나중에 내가 낸 \x01 오타를 즉시 잡아냈다.)

5-6. \b가 _ 앞에서 작동하지 않음

  • 증상: 스케줄에서 읽은 항차 전부 서비스가 빈값. 그래서 BK SHEET 헤더오타가 이겨버림.
  • 원인: \bCSC\b는 CSC_Schedule에 매칭되지 않는다. _가 단어문자이므로 CSC와 _ 사이에 경계가 없다.
  • 수정: (?:^|[^A-Z])(CSC|NWX|CCS|SKS)(?:[^A-Z]|$)
  • 교훈: \b는 [A-Za-z0-9_] 기준이다. 업무 라벨은 _를 구분자로 쓴다. 둘은 정면충돌한다.

5-7. 2개씩 순차 병합 → 파일 순서에 따라 결과가 달라짐

  • 증상: 파일을 정순/역순으로 넣으면 선명이 X-PRESS PHOENIX / X-PRESS PHOEINIX 로 갈림. 같은 배치를 반복 투입해도 1건이 계속 진동.
  • 원인: 빈칸을 낮은 신뢰도 사본이 먼저 채우면, 뒤에 온 높은 신뢰도 사본이 더 이상 고칠 수 없다. 어느 쪽이 먼저 오는지가 순서에 달려 있었음.
  • 수정: 쌍 병합 폐기 → 그룹 전체를 모아 신뢰도 정렬 후 필드별 선택.
  • 검증: 정순·역순·섞은 순서 3가지가 레코드 지문까지 완전 동일. ✅ 9가지 배치 조합 반복 투입에서 변경 0건. ✅
  • 교훈: "누적 병합"을 fold로 짜면 결합법칙이 깨지기 쉽다. 전량을 모아 한 번에 정렬해 결정하면 순서 의존이 원천 제거된다.

5-8. 원본을 덮어써서 무한 진동

  • 증상: 같은 파일을 계속 넣는데 매번 "1건 변경". svc1: NWX→CCS→NWX→…
  • 원인: 스케줄 기준으로 svc1을 덮어썼음. 다음 업로드에서 원본이다시 CCS를 주장 → 또 보정 → 영원히 반복.
  • 수정: svc1은 원본 그대로 두고 svcEff(파생)에 보정값. 집계는 svcEff 사용.
  • 교훈: 멱등성(idempotence)을 지키려면 읽은 값과 계산한 값을 섞지 말 것. "덮어쓰기"는 언제나 진동의 씨앗이다.

5-9. FULL을 자리표시자로 인식하지 못함

  • 증상: 부킹 3건 7 TEU가 사라짐.
  • 원인: B/L 자리에 FULL이 8번 쓰이는데 자리표시자 목록에 없어서, 서로 다른 부킹 3건이 하나의 키로 뭉개짐.
  • 수정: 자리표시자 집합 확장(MT FULL T.B.N TBA N/A PENDING …) + 등장 순번을 키에 포함.
  • 교훈: 업무 파일의 "빈칸"은 진짜 빈칸이 아니라 관용어다. 실데이터에서 짧고 반복되는 값을 세어보면 금방 드러난다.

5-9b. 파일 갱신 경로에서 자리표시자 B/L이 또 뭉개짐

  • 증상: 1회차는 정상. 갱신된 파일에 같은 학습을 또 넣으면 Empty Repo 3건이첫 번째 Empty Repo 행으로 몰려 값이 뒤섞임.
  • 원인: propagate의 매칭 키를 정규화한 B/L 하나로만 잡았음. 1회차에는대상 파일에 그 행들이 없어서(전부 신규) 문제가 드러나지 않았다.
  • 수정: 자리표시자 B/L은 선명|항차 + POL>F.POD + 비고문 복합 키로 매칭하고, 대상 행을 한 번씩만 소비(같은 키가 여러 행이면 순서대로 1:1 배정). 수량은 키에서 제외 — 수량 변경이 바로 갱신의 목적이므로.
  • 교훈: 같은 함정(§5-9)이 다른 코드 경로에 그대로 재발했다. 한 곳을고쳤다고 끝이 아니다. "이 식별 문제를 여기서도 풀어야 하나?"를 매번 물어야 한다.

5-9c. workbook.xml 수정이 저장되지 않음

  • 증상: _FilterDatabase 정의 이름이 $B$7:$AC$375에서 그대로. 자동 필터범위만 늘어나고 정의 이름은 안 늘어남.
  • 원인: open()에서 workbook.xml을 pkg.wbDoc에 따로 파싱해두고, save()는 pkg.docs[경로]만 순회했다. 같은 문서를 두 곳에서 다르게 들고 있었음.
  • 수정: docs['xl/workbook.xml'] = wbDoc 으로 한 객체를 공유.
  • 교훈: 같은 자원을 두 이름으로 들고 있으면 한쪽 수정이 조용히 사라진다.

5-11. 버튼이 하나도 안 눌리고 있었음 ⚠️⚠️

  • 증상: 탭 전환, 정렬, 실행 버튼이 전부 무반응. 콘솔 오류도 없음.
  • 원인: wire() 안에서 $('#btnLoadProj').addEventListener(...) — 그런 id가 index.html에 없어서 null.addEventListener로 TypeError. wire()가 거기서중단되고, 그 뒤에 등록되는 document.addEventListener('click', ...)가아예 붙지 않았다. 화면은 정상적으로 그려지므로 겉으로는 멀쩡해 보였다.
  • 왜 오래 못 찾았나: 검증할 때 FApp.tab = 'x'; FApp.rebuild()로 탭을 우회 전환했다. 사람이 실제로 클릭하는 경로를 한 번도 밟지 않았다.
  • 수정: on(sel, ev, fn) 헬퍼 — 요소가 없으면 그 하나만 건너뛰고 console.warn. 그리고 실제 .click()으로 전 탭·버튼·정렬·필터를 순회하는검증 단계를 추가.
  • 교훈: > 렌더링 검증은 상호작용 검증이 아니다. innerHTML.length > 0은 > "버튼이 눌린다"를 전혀 보장하지 않는다. > > 그리고 초기화 코드에서 한 줄의 실패가 뒤에 오는 전부를 죽이지 않게 하라.

5-10. PowerShell 5.1이 스크립트를 ANSI로 읽음

  • 증상: 바탕 화면 경로가 諛뷀깢 ?붾㈃로 깨져 파일을 못 찾음.
  • 수정: 스크립트에 비ASCII 리터럴을 두지 않고 [Environment]::GetFolderPath('Desktop')로 경로를 구성.
  • 교훈: Windows 한국어 환경 + PS 5.1에서는 스크립트 파일에 한글을 박지 말 것.
