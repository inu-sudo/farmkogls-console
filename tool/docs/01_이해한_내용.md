# 1단계 — 제가 이해한 팜코지엘에스의 업무와 데이터

이 문서는 제공해주신 13개 엑셀 파일과 알려주신 내용(회사명, 부킹 사이트,
"일부 항로는 사이트가 아니라 이메일 엑셀로 처리")을 근거로 재구성한
업무 모델입니다. **이 이해가 도구 설계의 전제**이므로, 틀린 부분이 있으면
이 문서를 먼저 고쳐야 합니다.

---

## 1. 회사가 하는 일

팜코지엘에스(Farmkogls, 데이터상 `FARMKO` / `팜코`)는 **선박을 소유하지 않는
NVOCC / 선복 재판매업자**입니다.

```
  피더 선사              팜코지엘에스                고객
  (GFS/BTL/X-Press)  ──▶  선복 블록 매입      ──▶  한국 포워더
   실제 배 운항            (DF 계약)                해외 에이전트
                          ↓
                    남은 선복 = 손실
                    초과 선복 = 추가비용
```

핵심 구조는 **DF(Dead Freight, 부동운임) 계약**입니다.

- 선사와 기간(보통 1~6개월)을 정해 **약정 물량(TEU)과 약정 중량(톤)**을 삽니다.
- 대금은 `TEU당 단가 × 약정 물량`으로 **고정**됩니다. → 안 채우면 그대로 손실.
- 약정을 넘겨 실으면 **Excess Slot Rate**(구간별 별도 단가)가 붙습니다.
- 여기에 할증이 더해집니다: DG 150/TEU, RF 150/box, Flexi 100/box,
  TK 100/box, COD 130/변경.

**따라서 이 회사의 손익은 "약정 대비 실제 적재율"에서 거의 다 결정됩니다.**
BSA를 넘겼는지 남겼는지가 곧 돈입니다. 제가 만든 도구가 화면 한가운데에
`BSA 대비 이용률`을 놓은 이유입니다.

실제 예 (`BTL_CCS(JUL 26')` 시트):

| 항목 | 값 |
|---|---|
| 단가 | 850 / TEU |
| 약정 물량 | 70 TEU |
| 약정 중량 | 910 톤 (상해 720 톤) |
| 고정 대금 | 59,500 |
| 실제 적재 | 69 TEU → 실질 단가 862.3 / TEU |
| 판매 단가 | 20' 1,500 / 40' 1,900 |
| 결과 | +12,850 |

같은 시트의 "#1. Ideal Booking" 시나리오는 **−16,000** 입니다. 즉
**어떤 박스를 싣느냐에 따라 흑자와 적자가 갈립니다.** 40'를 이상적으로 채우면
적자, 실제처럼 20'를 섞으면 흑자였습니다.

## 3. 오가는 문서 7종과 업무 흐름

이게 이 회사 업무의 실체입니다. 누가 → 누구에게 → 무엇을 보내는지:

```
 [해외 에이전트: MSA 등]
        │  ① 주간 부킹 예보 (학습.xlsx 형태)
        │     서비스별 4개 시트 · B/L 단위
        ▼
 [팜코 영업/운영]  ──②──▶ ③ 항차별 BK SHEET (마감)
        │                    선적 확정 · 판매운임 · 손익
   ② 통합 등록부                    │
   (FES BK FCST)                    ▼
   전 서비스 · 2구간 라우팅     ④ ROB 적재계획
        │                        구간별 잔여 선복
        ▼
   ⑤ 스케줄 / ⑥ BSA / ⑦ DF 계약  ← 선사와의 약정 (상수 역할)
```

| # | 문서 | 성격 | 담고 있는 것 |
|---|---|---|---|
| ① | `FES <SVC> BK FCST` (학습.xlsx) | 해외 에이전트 → 팜코, **주간 유입** | B/L, 선명/항차, ETD, POL/POD/F.POD, 컨테이너 수량, VGM |
| ② | `FES BK FCST` (FES AGENCY) | 팜코 **통합 등록부** | ①에 2구간(환적) 라우팅·고객·요율 추가. 하단에 `** CANCEL LIST` 별도 구역 |
| ③ | `BK SHEET (마감)` | **항차별 운영 확정본** | 부킹일/취소일, 선적인(한국 포워더), DG·OOG 특수화물, 픽업 터미널, 영업사원, **판매운임과 손익**, 헤더에 BSA·DF 단가·서류/화물 마감일. 하단에 `Cancel 정리` |
| ④ | `ROB` (항차별) | **적재 통제** | 기항지마다 이전 잔량 + 적재 − 양하 = 선상 잔량, NDG/DG/OOG 구분, BSA 대비 잔여 |
| ⑤ | `Schedule` | 상수 | 서비스별 기항 순서와 항구별 ETD, WEEKNUM |
| ⑥ | `BSA` | 상수 | 항차별 우리 배정량(TEU·톤), Northbound/Southbound, 선박 대체(`A => B`) |
| ⑦ | `DF 계산기` | 상수 | 선사·서비스·기간별 단가/약정량/할증/구간 초과단가 |

여기에 운임 파일들(`FES India 운임`, `NVOCC 월간 운임`, `파트너 월간운임`,
`IRAN & RED SEA`, `MARKET RATE`, `OOG 운임 포맷`)이 **반월 단위(1H/2H)**로
따로 관리됩니다. `FES India 운임`은 24년 6월부터 26년 7월까지 51개 시트가
쌓여 있습니다. FEEDER CARRIER / PRINCIPAL TERM(FIFO) / SELLING TERM(CY/CY) /
환율 / DG 할증(원가·판매 분리)이 한 시트에 함께 들어 있습니다.

## 4. 반드시 지켜야 하는 계산 규칙

파일의 실제 수식에서 그대로 뽑았습니다. 도구도 동일하게 구현했습니다.

**TEU 환산** — 20피트류 1, 40피트류 2, Void 1
```
TEU = 20'DV + 20'MT + 20'FR + Void + (40'HC + 40'MT + 40'FR) × 2
```
`Void`가 1 TEU로 계산되는 게 중요합니다. OOG(초과규격) 화물이 옆 슬롯을
못 쓰게 만드는 만큼을 비용으로 잡는 것입니다.

**주차(WK)** — 엑셀 `WEEKNUM(ETD)` 기본값(일요일 시작, 1월 1일이 1주차).
ISO 주차와 다릅니다. 파일과 숫자를 맞추려면 이 방식이어야 합니다.

**Tare(공컨 자중)** — 20FT 2.3톤, 40FT 3.7톤

**화물 등급** — FR이나 Void가 있으면 `OOG`, 특수/비고에 위험물 표기가 있으면
`DG`, 나머지는 `NDG`

**ROB(선상 잔량)** — 이게 가장 중요한 개념입니다.
```
각 기항지에서:  잔량 = 이전 잔량 + 이번 적재 − 이번 양하
잔여 선복    =  BSA − 최대 선상 잔량
```
**"부킹 합계"가 아니라 "최대 선상 잔량"이 선복 소요량**입니다.
부산에서 실어 첸나이에서 내린 박스는 그 이후 구간의 선복을 쓰지 않습니다.
실제 예 — `TIGER CHENNAI 2605W`는 부킹 합계 105 TEU지만
최대 선상 잔량은 81 TEU입니다. 귀사 BK SHEET의 Grand Total도 81입니다.
BSA가 50이므로 초과는 31 TEU(합계 기준 55가 아님)입니다.
**이 차이만큼 초과 선복 비용을 과다 계산할 수 있습니다.**

## 5. 지금 방식의 구조적 문제

부킹 사이트(farmkogls.plism.com)가 있는데도 엑셀을 주고받는 이유가
"일부 항로만 사이트에서 처리된다"는 것이었습니다. 그래서 생기는 문제:

1. **같은 부킹이 3곳에 존재** — 에이전트 예보, 통합 등록부, 항차 BK SHEET.
   서로 값이 어긋나도 알 방법이 없습니다.
   실제로 지금 파일에 **16건의 불일치**가 있습니다.
2. **수식이 조용히 깨져 있음** — `FES BK FCST`의 VGM 계산 중
   16·21·23·24·30·31·37·38·39행이 빈 셀 `$V$4/$V$5`를 참조해 **중량이 0**으로
   나옵니다(정상인 26·29행은 `$Z$4/$Z$5`). 중량 초과 판단이 무력화됩니다.
3. **표기 불일치** — 같은 항구가 `MYPKG(N)` / `MYPKN` / `NPKL`,
   같은 회사가 `FARMKO` / `팜코`, 오타 `CHSHA`(→CNSHA),
   `X-PRESS PHOEINIX`, `MELBOURNE BRDIGE`.
   → 집계하면 각각 다른 항목으로 잡힙니다.
4. **헤더 오타가 실적을 왜곡** — BK SHEET 5장의 `SVC Name`이 잘못 적혀
   **80건의 부킹이 엉뚱한 서비스로 집계**되고 있었습니다.
   예: `XCA26022W(0615)마감`은 CSC로 적혀 있지만 X-PRESS CARINA는 NWX 선박입니다.
5. **항차 번호가 매년 재사용됨** — `WAN HAI 522 W038`이 25년과 26년에 모두
   존재합니다. 연도 구분 없이 합치면 과거 BSA가 현재 항차를 덮어씁니다.
6. **초과 적재가 집계되지 않음** — 지금 데이터에서 **27개 항차가 BSA 초과,
   합계 476 TEU**입니다. 의도된 초과일 수도 있지만, 한눈에 보이지 않으면
   협상·정산 근거가 없습니다.

## 6. 그래서 도구가 하는 일

위 문제를 1:1로 겨냥했습니다.

| 문제 | 도구의 대응 |
|---|---|
| 같은 부킹 3중 존재 | B/L+항차+POD 키로 병합, 어긋난 값은 **양쪽 출처를 명시해 보고** |
| 표기 불일치 | 항구·선박·거래처 표준화 사전 |
| 헤더 오타 | 그 항차의 스케줄이 이기고, 정정 내역을 보고 |
| 항차번호 재사용 | BSA 출처에 우선순위(항차 BK SHEET > 스케줄 > 과거 ROB) |
| 초과 적재 미집계 | ROB를 재계산해 **최대 선상 잔량** 기준으로 BSA 대비 표시 |
| 수식 파손 | 수량에서 TEU·중량을 직접 재계산, 원본과 다르면 경고 |
| 주간 반복 작업 | 파일 드롭 → 누적 등록부 → 엑셀 1클릭 출력 |

검증 결과(제공된 6개 파일 기준): 부킹 1,182건 · 4,920 TEU · 항차 166개.
엑셀에서 열어 `MASTER` / `VOYAGE SUMMARY` / `WEEK SUMMARY` 합계가
모두 4,920으로 일치합니다.

## 7. 아직 확인이 필요한 부분 (제 추정)

정직하게 적어둡니다. 이 항목들은 제가 데이터에서 추론한 것이라 확인이 필요합니다.

1. **`Void` 1 TEU 처리** — 파일 수식을 따랐지만, 실제 선사 정산에서
   Void를 어떻게 청구하는지는 확인이 필요합니다.
2. **BK SHEET의 `Shipper`와 통합 등록부의 `BK PARTY`** — 전자는 한국 포워더,
   후자는 해외 에이전트로 성격이 다른데, 도구는 둘을 "부킹 주체" 하나로
   묶었습니다. 분리해야 하면 알려주세요.
3. **손익** — 항차 BK SHEET에 DF 원가가 적힌 항차만 마진을 계산했습니다.
   초과 선복 단가와 할증은 참고용으로만 읽어두고 마진에 반영하지 않았습니다.
   전체 손익을 원하시면 DF 계약과 항차를 기간으로 연결해야 합니다.
4. **`JIRA BHUM` / `HEMMA BHUM` / `MUMBAI BRIDGE`** — 스케줄에 없어
   서비스를 데이터에서 학습했습니다. RCL 관련 선박으로 보이는데
   어느 루프인지 확인이 필요합니다.
5. **운임 파일 6종** — 구조는 파악했지만 도구에 아직 연결하지 않았습니다.
   판매운임 자동 적용까지 원하시면 다음 단계입니다.
