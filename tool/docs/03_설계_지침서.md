# 3단계 — 설계 지침서

두 가지 용도로 씁니다.

1. **내가 이해하기** — 코드를 한 줄도 안 읽고 이 도구가 어떻게 굴러가는지 파악
2. **남에게 설명하기** — 팀장, 동료, IT 담당자에게 그대로 읽어줘도 통하는 설명

코드는 한 줄도 나오지 않습니다. 기술 상세가 필요하면 [부록](04_기술_참고.md)으로.

---

## 1. 한 문장으로

> **여러 곳에서 온 엑셀을 하나의 장부로 합쳐서, 배에 실제로 몇 개가 실리는지
> 계산하고, 다시 엑셀로 내보내는 프로그램.**

길이별 설명 대본:

**30초 (엘리베이터)**
> 지금은 에이전트가 보낸 예보, 우리 통합 등록부, 항차별 마감 시트가 따로 있어서
> 같은 부킹이 세 군데에 있고 값이 다를 때 알 방법이 없습니다. 이걸 파일 하나에
> 끌어다 놓으면 자동으로 합쳐서, 어느 항차가 BSA를 넘겼는지 바로 보여주고
> 통합 엑셀로 내보냅니다. 설치도 로그인도 없고, 데이터는 PC 밖으로 안 나갑니다.

**1분 (실무자에게)**
> 매주 하던 일이 그대로 남아 있습니다. 엑셀을 받고, 통합하고, 회신하는 것.
> 달라지는 건 통합을 손으로 안 한다는 것뿐입니다. 파일을 끌어다 놓으면
> 지난주와 뭐가 바뀌었는지, 어느 부킹이 파일마다 값이 다른지, 어느 항차가
> 선복을 넘겼는지를 목록으로 뽑아줍니다. 결과물도 우리가 쓰던 열 순서 그대로
> 나오니까 받는 쪽에서 위화감이 없습니다.

**3분 (경영진에게)** — §7의 대본 사용

## 2. 비유로 보는 전체 구조

**여러 나라에서 서류가 들어오는 사무실**이라고 생각하면 정확합니다.
다섯 명이 순서대로 일합니다.

```
   ①접수원        ②번역가        ③장부담당       ④회계사        ⑤비서
      │              │              │              │              │
  어떤 양식이든   표기를 하나로   같은 건인지    배에 실제로    보고서 인쇄
   읽어낸다      통일한다        판단해 대장에   몇 개 실리는지   화면 표시
                                올린다          계산한다
```

| 담당 | 하는 일 | 구체적으로 |
|---|---|---|
| **①접수원** | 양식을 가리지 않고 읽는다 | 시트 이름이 `마감`이든 `(0726)`이든 상관없이, **표의 머리글을 보고** "이건 에이전트 예보", "이건 항차 마감 시트"라고 판별 |
| **②번역가** | 같은 걸 같다고 만든다 | `MYPKG(N)` `MYPKN` `NPKL` → 모두 클랑(북). `FARMKO` `팜코` → 한 회사. `CHSHA` 오타 → 상해 |
| **③장부담당** | 중복은 합치고, 다르면 보고 | 같은 B/L이 세 파일에 있으면 한 줄로. 값이 어긋나면 **어느 파일에서 뭐라고 했는지 양쪽 다 적어서 보고** |
| **④회계사** | 진짜 숫자를 낸다 | 기항지 순서를 따라가며 실었다 내렸다를 계산해 **최대 동시 적재량**을 구함 |
| **⑤비서** | 사람이 읽을 형태로 | 화면 6개 탭 + 엑셀 14시트 |

**이 순서가 곧 프로그램 구조입니다.** 파일 하나를 열어보면
`zip → xlsx-read → parse → normalize → merge → aggregate → ui/export`
순서로 되어 있는데, 위 다섯 명과 1:1로 대응합니다.

AI에게 수정을 맡길 때 **"어느 담당의 일인가"만 짚어주면 됩니다.**
"항구 표기가 하나 더 있어" → 번역가(②). "새 양식이 왔어" → 접수원(①).

### 그리고 여섯 번째 — 「편집자」

주 업무인 **파일 갱신**은 위 흐름과 다른 길을 갑니다.
집계해서 새 보고서를 쓰는 게 아니라, **기존 등록부를 펼쳐놓고 필요한 줄만 고쳐 씁니다.**

```
   ①접수원        ②번역가        ⑥편집자
      │              │              │
  학습.xlsx를     표기 통일      기존 등록부를 열어
   읽는다                        · 있는 건은 그 줄을 고치고
                                · 없는 건은 줄을 끼워 넣고
                                · 밀려난 아래쪽을 정리하고
                                → 새 사본으로 저장
```

편집자는 **원고 전체를 다시 타이핑하지 않습니다.** 그래서 손대지 않은 부분
(수식·서식·그림·메모·다른 시트)이 그대로 남습니다. 이게 설계 결정 ③-0입니다.

담당 모듈: `xlsx-edit.js`(파일 정밀 편집) + `propagate.js`(어느 칸에 무엇을 쓸지).

## 3. 왜 이렇게 만들었나 — 결정 5개

각 결정마다 **"다르게 했다면 어떻게 됐을까"**를 붙였습니다.
설명할 때 이 대비가 제일 잘 먹힙니다.

### ① 설치가 필요 없는 파일 하나로

**다르게 했다면** — 서버를 세우고 계정을 만들고 사내 IT 승인을 받아야 합니다.
담당자가 바뀌면 인수인계에 "이 서버 관리법"이 추가됩니다.

**이렇게 한 이유** — 이 PC에는 개발 도구가 하나도 깔려 있지 않았습니다.
프로그램 설치 권한이 없거나 IT 승인이 오래 걸리는 환경에서도
**더블클릭 한 번**으로 돌아가야 했습니다. 파일 하나(192KB)라서
메일로 보내면 그게 곧 배포입니다.

### ② 인터넷을 전혀 쓰지 않음

**다르게 했다면** — 부킹 데이터, 고객명, 운임이 외부 서버를 거칩니다.
"이 도구 써도 되나요?"를 보안팀에 물어야 합니다.

**이렇게 한 이유** — 실을 수 있는 물량, 판매 단가, 거래처 목록은
**경쟁 정보**입니다. 외부로 나가는 통신이 **한 건도 없게** 만들었습니다.
와이파이를 끄고 써도 똑같이 동작합니다. 이건 IT 담당자에게
"통신 안 합니다"로 한 문장에 설명됩니다.

> 이 때문에 엑셀을 읽고 쓰는 기능을 남의 라이브러리 안 쓰고 직접 만들었습니다.
> 라이브러리를 쓰면 그걸 인터넷에서 받아와야 하거나 파일이 5배로 커집니다.

### ③-0. 파일을 새로 만들지 않고, 기존 파일을 고침 ⭐⭐

**다르게 했다면** — "통합 결과"라는 새 엑셀을 하나 만들어 줍니다. 그런데 그건
담당자가 쓰던 등록부가 아닙니다. 수식도 서식도 그림도 메모도 없는 딴 파일입니다.
결국 사람이 그걸 보고 원래 등록부에 다시 옮겨 적어야 합니다. **일이 안 줄어듭니다.**

**이렇게 한 이유** — 원하는 건 "새 보고서"가 아니라 **"내 파일이 갱신된 것"**입니다.
그래서 대상 파일을 통째로 다시 만들지 않고, **필요한 칸만 골라서 고칩니다.**

집을 새로 짓는 게 아니라 **벽지만 바르는 것**에 가깝습니다. 건드리지 않은 부분은
1비트도 바뀌지 않으니 수식·서식·그림·메모가 원래대로 남습니다.

행을 새로 끼워 넣을 때 따라 움직여야 하는 것들이 있습니다 — 아래쪽 수식의 행 번호,
조건부 서식 범위, 메모 위치, 자동 필터 범위, 정의된 이름. 엑셀이 손으로 삽입할 때
해주는 일을 프로그램이 대신 합니다. 실제 파일에서 그 항목이 **11가지**였고, 전부
열거해서 하나씩 맞췄습니다. 검증은 엑셀로 직접 열어서 했습니다 —
**"복구가 필요합니다" 없이 열리고, 새 행의 수식이 실제로 계산되고,
`Schedule` 시트 셀 차이가 0**이어야 통과입니다.

### ③ 엑셀을 없애지 않고, 엑셀을 그대로 씀 ⭐

**다르게 했다면** — "이제 엑셀 그만 쓰고 이 시스템에 직접 입력하세요"가 됩니다.
해외 에이전트, 선사, 한국 포워더 **전부**를 설득해야 합니다. 실패합니다.

**이렇게 한 이유** — 엑셀 주고받기는 **없앨 수 없는 현실**입니다.
상대가 우리 시스템을 쓸 이유가 없으니까요. 그래서 도구는
**받는 엑셀도 그대로, 보내는 엑셀도 그대로**입니다.
내보낸 파일의 열 순서를 귀사 `FES BK FCST`와 똑같이 맞춘 게 그 이유입니다.
받는 쪽에서는 뭐가 바뀐 줄도 모릅니다.

바뀌는 건 **중간의 손작업만** 입니다.

### ④ 원본 값을 절대 고치지 않음

**다르게 했다면** — 도구가 "이 서비스는 틀렸으니 고쳐놨습니다" 하고
값을 바꿔버립니다. 나중에 원래 뭐였는지 알 수 없습니다.

**이렇게 한 이유** — 원본은 그대로 두고, 보정한 값을 **옆 칸에 따로** 둡니다.
집계는 보정값으로 하고, 화면에는 ⚑ 표시를 붙여 "원본은 이랬다"를 볼 수 있게 합니다.

이걸 어겼다가 실제로 사고가 났습니다 — 원본을 덮어쓰니까,
다음에 같은 파일을 넣으면 원본이 다시 자기 값을 주장하고, 또 고치고,
**무한 반복**됐습니다(§5-③).

### ⑤ 값이 충돌하면 조용히 정하지 않음

**다르게 했다면** — 도구가 알아서 하나 고릅니다. 편하지만,
**틀렸을 때 아무도 모릅니다.**

**이렇게 한 이유** — 규칙대로 하나를 고르되 **버린 값과 양쪽 출처를 전부 기록**합니다.
`Changes › Source disagreements`와 엑셀 `DATA QUALITY` 시트에
"이 B/L의 ETD가 A파일은 7/31, B파일은 7/27. 7/31을 썼습니다"가 남습니다.

**통합 도구의 신뢰는 여기서 결정됩니다.** 사람이 모르게 값을 고르기 시작하면
아무도 결과를 믿지 않습니다.

## 4. 가장 중요한 아이디어 3개

기술이 아니라 **업무 통찰**입니다. 이 셋만 이해하면 도구를 다 이해한 겁니다.

### ① 선복은 "합계"가 아니라 "최대 동시 점유" — 호텔 객실과 같다 ⭐⭐

> **호텔에 한 달간 100명이 묵었다고 방 100개가 필요한 게 아닙니다.
> 같은 날 밤에 최대 몇 명이 있었는지가 필요한 방 수입니다.**

배도 똑같습니다. 부산에서 실어 첸나이에서 내린 컨테이너는
**그 이후 구간의 선복을 쓰지 않습니다.**

실제 숫자로:

| | TIGER CHENNAI 2605W |
|---|---|
| 부킹 합계 | 105 TEU |
| **최대 동시 적재** | **81 TEU** ← 실제 필요한 선복 |
| BSA(우리 배정) | 50 TEU |
| 초과 | **31 TEU** (합계로 보면 55로 착각) |

귀사 BK SHEET의 Grand Total도 81입니다. 즉 **원래 이렇게 세고 계셨고**,
도구가 그걸 자동화한 것입니다. 합계로 계산하면 초과 선복 비용을
**24 TEU만큼 과다 계상**합니다.

그래서 화면에 `Booked TEU`와 `Peak TEU`를 나란히 놓았습니다.
정산 근거는 항상 `Peak`입니다.

### ② 같은 부킹인지 어떻게 알아보나 — 주민번호가 있는 사람과 없는 사람

세 파일에 흩어진 부킹이 "같은 건"인지 판단해야 합니다.

**B/L 번호가 있으면 쉽습니다** — 주민번호처럼 씁니다.
`B/L번호 + 선명·항차 + 양하항`이 같으면 같은 건.

**문제는 B/L이 없는 행입니다.** 공컨 회수는 B/L 자리에 `MT`, `FULL`,
`T.B.N`처럼 적혀 있습니다. 주민번호 없는 사람을 구별하는 셈입니다.
그래서 **얼굴 특징을 조합**합니다 — 항차 + 구간 + 거래처 + 박스 구성 + 비고,
**그리고 "그 시트에서 몇 번째로 나온 같은 모양인지"**.

마지막 조건이 없으면 사고가 납니다. 같은 시트에 똑같이 생긴 공컨 3줄이
실제로는 별개 부킹인데 1줄로 뭉개집니다. 실제로 **3건 7 TEU가 사라지고**
있었습니다(§5-①).

**부작용도 정직하게**: 그 행의 비고를 고치면 새 행처럼 보입니다.
매뉴얼 §9에 적어뒀습니다.

### ③ 파일 넣는 순서가 결과를 바꿔선 안 된다 — 장부는 정리 순서와 무관하다

영수증을 어떤 순서로 정리하든 월말 합계는 같아야 합니다.
당연한데, 프로그램에서는 당연하지 않습니다.

처음엔 **파일을 들어오는 대로 둘씩 합쳤습니다.** 그러면 이런 일이 생깁니다:

> 빈칸을 신뢰도 낮은 파일이 먼저 채워버리면,
> 나중에 온 신뢰도 높은 파일이 **더 이상 고칠 수 없습니다.**

정순으로 넣으면 선명이 `X-PRESS PHOENIX`, 역순으로 넣으면 `X-PRESS PHOEINIX`가
됐습니다. 같은 데이터인데요.

**해결** — 둘씩 합치는 걸 버리고, **같은 부킹의 사본을 전부 모아놓고
신뢰도 순으로 줄 세운 다음, 항목마다 "값을 가진 가장 신뢰도 높은 사본"에서**
가져옵니다.

신뢰도 순서(설명할 때 이대로 쓰면 됩니다):
1. **항차별 마감 시트** — 실제 선적 확정본이니 가장 정확
2. **통합 등록부 / 에이전트 예보** — 같은 등급
3. 같은 등급이면 **더 최근에 저장된 파일**
4. 그래도 같으면 파일명 순서 (결과가 항상 같게 하려고)

검증: 정순·역순·섞은 순서 세 가지가 **완전히 동일한 결과**.
9가지 파일 조합을 반복 투입해도 변경 0건.

## 5. 실패에서 배운 것 (비개발자에게 설명하기 좋은 사례)

"AI로 만들었는데 믿을 수 있나요?"라는 질문에 대한 답이 이 절입니다.
**만드는 동안 조용히 틀린 답을 내던 문제 10개를 찾아 고쳤습니다.**
전부 에러 메시지 없이, 그럴싸한 숫자를 내놓고 있었습니다.

대표 3개만 (전체는 [부록](04_기술_참고.md) §5):

### ① 부킹 3건이 사라지고 있었음
B/L 자리에 `FULL`이라고 적힌 행 8개를 프로그램이 "빈칸"으로 못 알아봤습니다.
그래서 서로 다른 부킹 3건이 1건으로 합쳐졌습니다. **7 TEU가 조용히 사라졌습니다.**
→ 교훈: 업무 파일의 "빈칸"은 진짜 빈칸이 아니라 **관용어**다.

### ② 같은 화물을 두 번 실었다고 계산
CCS 항로는 청도와 부산을 **두 번** 기항합니다. 프로그램이 항구 이름만 보고
매칭해서, 첫 기항에서 실은 화물을 마지막 기항에서 또 실었습니다.
필요 선복이 42 TEU인데 **75 TEU로 계산**됐습니다.
→ 교훈: 항로는 "항구 목록"이 아니라 **순서가 있는 여정**이다.

### ③ 같은 파일을 넣을 때마다 값이 바뀜
"이 서비스 표기가 틀렸다"고 판단해서 원본을 고쳐놨더니,
다음에 같은 파일을 넣으면 원본이 다시 자기 값을 주장하고, 또 고치고,
**영원히 왔다갔다** 했습니다.
→ 교훈: 읽은 값과 계산한 값을 **섞지 말 것.**

### ④ 버튼이 하나도 안 눌리고 있었음 ⚠️ (가장 부끄러운 것)

화면을 만들 때, 존재하지 않는 버튼(`btnLoadProj`)에 기능을 붙이는 코드가
한 줄 있었습니다. 그 한 줄에서 오류가 나면서 **그 뒤에 등록되는 모든 클릭 기능이
통째로 죽었습니다.** 탭 전환도, 정렬도, 실행 버튼도 전부 안 눌렸습니다.

**그런데 오랫동안 못 찾았습니다.** 제가 검증할 때 화면을 "그려지는지"만 확인하고
버튼은 프로그램으로 우회해서 눌렀기 때문입니다. 사람이 실제로 클릭하는 경로를
한 번도 안 밟았습니다.

→ 교훈 둘:
> **화면이 그려지는 것과 눌리는 것은 다른 문제다.** 반드시 실제로 클릭해서 확인.
>
> 그리고 **한 곳의 오류가 다른 기능까지 죽이지 않게** 만들어야 합니다.
> 이제는 없는 버튼을 만나면 그 하나만 건너뛰고 경고를 남깁니다.

### 그래서 검증을 5중으로 걸었습니다

| 단계 | 확인하는 것 |
|---|---|
| 1 | 원본 파일로 전 과정 실행 + 알려진 셀 값 18개 대조 |
| 2 | 같은 파일 반복 투입 → **변경 0건**이어야 통과 |
| 3 | 파일 순서를 바꿔도 → **완전히 같은 결과**여야 통과 |
| 4 | **실제로 클릭해서** 탭·버튼·정렬·필터가 다 동작하는지 (④의 교훈) |
| 5 | **엑셀로 실제로 열어서** 복구 없이 열리는지, 수식이 계산되는지, 한글이 살았는지 |

5번이 최종 관문입니다. 확인한 것:
- 분석 리포트: 엑셀이 계산한 합계 **4,920 TEU가 3개 시트에서 전부 일치**
- 파일 갱신: **"복구가 필요합니다" 없이 열림**, 새 행의 `=WEEKNUM`·TEU 수식이
  실제 계산됨, 서식·그림·메모 보존, `Schedule` 시트 **셀 차이 0**,
  TEU 합계 증가분 116이 신규 11행 합계와 정확히 일치

### AI에게 줄 프롬프트 틀

```
farmkogls-console 폴더의 도구를 수정해줘.

[먼저 읽을 것]
docs/03_설계_지침서.md 와 docs/04_기술_참고.md 를 먼저 읽어.
특히 04의 §5(실제 버그 10건)와 §8(함정 12개)를 지켜줘.

[요청]
(여기에 하고 싶은 것)

[반드시 지킬 것]
- 외부 라이브러리나 인터넷 통신을 추가하지 마
- 소스에서 읽은 원본 값을 덮어쓰지 마 (파생 필드를 써)
- 값 충돌을 조용히 처리하지 마 (반드시 기록하고 보고해)

[수정 후 검증]
1. python farmkogls-console/build.py  가 통과하는지
2. test.html 과 test-prop.html 이 원본 파일로 끝까지 도는지
3. 같은 파일을 두 번 넣었을 때 "변경 0건"인지
4. 파일 순서를 뒤집어도 결과가 같은지
5. 브라우저에서 탭·버튼·정렬·필터를 실제로 click() 해서 다 동작하는지
```

**5번을 안 해서 "버튼이 하나도 안 눌리는" 버그를 한참 놓쳤습니다.**

코드를 못 읽어도 이건 할 수 있습니다.

1. **파일 갱신**: 학습.xlsx + FES AGENCY를 넣고 **신규 11 · 갱신 5**가 나오는지

   있고 `H`·`Y`열에 숫자가 계산돼 있는지
3. 그 파일을 다시 넣었을 때 **신규 0 · 갱신 0**인지 (중복 방지 확인)
4. **탭을 마우스로 하나씩 눌러보고** 전부 바뀌는지

### 팀장 / 경영진용 (돈 이야기)

> 우리 손익은 선사와 약정한 선복을 얼마나 정확히 채우는지에서 거의 다

> 근거 자체가 없었습니다.
>

> 수식 9곳이 빈 셀을 참조해 **중량이 0으로 나오고** 있었습니다.
>
> 비용은 들지 않습니다. 파일 하나이고, 설치도 서버도 없고, 데이터는
> 회사 PC를 벗어나지 않습니다.

### 동료 실무자용 (일이 어떻게 편해지나)

> 하는 일은 그대로예요. 엑셀 받고, 합치고, 회신하는 것.

> 다르면 "이 파일은 7/31, 저 파일은 7/27"까지 다 찍어줍니다.
>
> 같은 파일을 여러 번 넣어도 아무 일 안 생기고, 넣는 순서도 상관없어요.
> 잘못 넣었나 걱정 안 해도 됩니다.
>
> 내보내는 엑셀은 우리가 쓰던 열 순서 그대로라서 받는 쪽에서 위화감 없어요.

## 8. 최소 용어집

| 도구 용어 | 업무 말로 |
|---|---|
| 등록부 (register) | 누적 부킹 대장 |
| 병합 (merge) | 여러 파일을 대장에 합쳐 넣기 |
| 정규화 (normalize) | 표기 통일 (`MYPKN` = `NPKL`) |
| 키 (key) | 같은 부킹인지 판단하는 기준 |
| Peak TEU | 최대 동시 적재량 = 실제 필요 선복 |
| 멱등성 (idempotent) | 같은 파일을 몇 번 넣어도 결과가 같음 |
| 파생 필드 | 원본을 안 고치고 옆 칸에 계산해둔 값 |
| 로컬 저장소 | 브라우저가 이 PC에만 저장하는 공간 |
| 프로젝트 파일 (.json) | 대장 전체 백업본 |
